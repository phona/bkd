# BUG-004 Fix terminal PTY session leak exhausting session limit

- **status**: completed
- **priority**: P0
- **owner**: claude (pma)
- **createdAt**: 2026-06-06 13:48

## Description

The in-app terminal no longer opens — it spins on "loading" forever.

Root cause (reproduced against the running deploy): `POST /api/terminal` returns
`429 {"success":false,"error":"Session limit reached"}`. `MAX_SESSIONS = 10`
(`apps/api/src/routes/terminal.ts`) is saturated and never recovers because PTY
shells leak: 181 live `/bin/bash -l` processes are parented by the launcher
(pid 1472491) while the ProcessManager only tracks 10.

Leak chain:
1. Terminal spawns a Bun PTY via `Bun.spawn([shell,'-l'], { terminal })` then
   force-casts it to the node-style `Subprocess` (`terminal.ts:180`
   `as unknown as Subprocess`).
2. `killSession()` (`terminal.ts:87`) calls `pty.terminal?.close()` +
   `terminalPM.forceKill()` (`handle.kill(9)`) — neither actually kills the
   underlying `bash` for this Bun PTY handle.
3. It then unconditionally calls `terminalPM.remove(id)` — frees the PM slot but
   orphans the live shell. Every closed terminal leaks one shell.

Because slot accounting and real process death diverge, the live cap (10) gets
saturated and the terminal stops opening.

Acceptance criteria:
- Closing / grace-expiring a terminal session actually terminates the shell
  (verified via process table — no orphan `/bin/bash -l` accumulation).
- A session slot is only released after the process is confirmed dead
  (`.exited` resolved), so accounting and reality cannot diverge.
- Stale/dead sessions are reaped on a sane cadence (not 24h).
- `POST /api/terminal` succeeds again under normal repeated open/close.

Note: the running instance is the compiled launcher build; the fix requires a
rebuild + redeploy of the launcher to take effect. A separate operational step
clears the currently leaked shells without restarting the launcher or the live
agents.

## Completion notes (2026-06-06)

Root cause refined during investigation: the kill code was NOT broken (a Bun
1.3.13 repro showed `terminal.close()` / `kill(9)` / process-group kill all work
in dev; SIGTERM does not — bash `-l` ignores it). The leak came from:
1. sessions created whose WS never attached (grace timer only armed on WS close)
   → never reaped until 24h;
2. `killSession` releasing the slot before confirming death;
3. the 429 path using `proc.kill()` (SIGTERM) — leaked the just-spawned shell.

Fix (`apps/api/src/routes/terminal.ts`):
- `killPty()` helper: `terminal.close()` + process-group SIGKILL
  (`process.kill(-pid, 9)`) + `kill(9)` fallback; used by `killSession` and the
  429 path.
- Unattached-session reaper armed on `POST` (`BKD_TERMINAL_UNATTACHED_MS`,
  default 30s), cleared on WS `onOpen` (`everAttached`).
- Periodic reconcile (now 60s) also reaps entries whose pid is already dead.

Tests: `apps/api/test/terminal-lifecycle.test.ts` (killPty kills the shell;
unattached session reaped). Process suites green. Lint + typecheck clean.

DEPLOYED (2026-06-06): packaged `0.0.188-lc`, installed to
`/workspace/data/app/v0.0.188-lc/`, activated via
`POST /api/settings/upgrade/apply-local`. Engine-core hash matched 0.0.187-lc +
no new migrations → HOT-RELOAD (launcher pid 1472491 unchanged, 7 agents stayed
alive). Verified `POST /api/terminal` → 200 (was 429). Fix live.

OPTIONAL remaining cleanup: ~217 pre-existing orphan `/bin/bash -l` shells from
the old leak are still running (now untracked, no longer block the cap, but waste
memory). Killing them needs explicit approval and is non-restart-safe.
